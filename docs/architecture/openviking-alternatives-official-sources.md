# OpenViking alternatives: official-source findings

Historical shortlist. Prefer the later [strategy research](../research/agentic-memory-strategies.md) for current-versus-legacy Letta/Mem0 distinctions and the [engine planning review](agentic-memory-engine-design.md) for the proposed product choice. Candidate rankings and vendor metrics below are dated observations, not selected dependencies or independently reproduced results.

Checked 2026-09-05. Sources below are first-party repositories, documentation, and benchmark pages. Vendor benchmarks are claims, not an independent apples-to-apples comparison.

## Shortlist

| Project | Main implementation | License | What it is | First-party performance claim / caveat |
|---|---|---|---|---|
| [Hindsight](https://github.com/vectorize-io/hindsight) | Python 3.11+ service; Python/TS/Go clients | MIT | Full agent-memory service: LLM extraction into facts/entities/relationships/time series; semantic, BM25, graph, and temporal retrieval in parallel; RRF + cross-encoder reranking; Postgres + pgvector (or Oracle) | [Benchmark page](https://benchmarks.hindsight.vectorize.io/) reports LongMemEvalS 94.6%, LoCoMo10 92%, BEAM 1M 73.9%, BEAM 10M 64.1%. The repository says Hindsight results were reproduced by Virginia Tech and The Washington Post, but this remains the project's own presentation. |
| [Supermemory](https://github.com/supermemoryai/supermemory) | Mostly TypeScript/Bun; packaged local binary | MIT | Full context stack: document/RAG ingestion, conversational fact extraction, contradiction/expiry handling, user profiles, hybrid search, connectors, embedded local graph engine | [README](https://github.com/supermemoryai/supermemory) claims 95% Recall@15 on LongMemEval with about 720 context tokens and about 50 ms user-profile reads. [Self-host docs](https://github.com/supermemoryai/supermemory/blob/main/apps/docs/self-hosting/quickstart.mdx) state production uses proprietary tuned models while self-hosting is bring-your-own-model, so hosted benchmark results should not be assumed for OSS self-hosting. |
| [Cognee](https://github.com/topoteretes/cognee) | Python 3.10+; separate [Rust port](https://github.com/topoteretes/cognee-rs) | Python: Apache-2.0; Rust: MIT OR Apache-2.0 | Knowledge-graph memory pipeline: ingest -> graph extraction (`cognify`) -> hybrid graph/vector retrieval. Python defaults include LanceDB and graph storage. Rust port has an Axum API, embedded Ladybug graph, embedded LanceDB vector store, SQLite metadata, local ONNX embeddings, and Python/TS/Java/C bindings. | Python README reports BEAM 0.79 at 100K and 0.67 at 10M with default OSS features. Rust README claims about 350 ms startup and 260 ms search, but gives no workload/methodology there; the BEAM scores are not identified as Rust results. Rust port is v0.2.0 and its docs explicitly list some closed companion adapters. |
| [Mem0](https://github.com/mem0ai/mem0) | Python core plus TypeScript SDK/implementation | Apache-2.0 | Memory extraction and retrieval layer over configurable LLM, embedding, vector, graph, and SQL providers. Current design is ADD-only extraction with semantic + BM25 + entity + temporal scoring. | [Official evaluation docs](https://docs.mem0.ai/core-concepts/memory-evaluation) report LoCoMo 92.5, LongMemEval 94.4, BEAM 1M 64.1, BEAM 10M 48.6, p50 around 0.88–1.09 s in the repo table. Crucial caveat: the docs say these scores use the managed platform's proprietary optimizations and OSS users should not expect identical results. |
| [Graphiti](https://github.com/getzep/graphiti) / Zep | Graphiti: Python 3.10+; current Zep managed engine is proprietary | Graphiti: Apache-2.0 | Temporal knowledge graph with episodic, semantic/entity, and community subgraphs; vector + full-text + graph traversal candidate generation and reranking. Graphiti requires Neo4j, FalkorDB, or Neptune. Zep is the managed production service, not the same deployable OSS engine. | [Zep paper](https://blog.getzep.com/content/files/2025/01/ZEP__USING_KNOWLEDGE_GRAPHS_TO_POWER_LLM_AGENT_MEMORY_2025011700.pdf) reports 94.8% DMR and LongMemEval 71.2% with GPT-4o, 2.58 s latency, and 1.6K context tokens versus 60.2%, 28.9 s, and 115K tokens for full context. These measurements used hosted Zep; they do not establish Graphiti OSS throughput. |
| [Letta](https://github.com/letta-ai/letta) | Python server; TypeScript/Python clients | Apache-2.0 | Stateful-agent runtime rather than a drop-in context database. Uses editable in-context memory blocks, recall/archival memory, summaries, and newer git-backed MemFS. | [Letta research](https://www.letta.com/research/) reports a filesystem approach scoring 74.0% on LoCoMo. This is a memory-quality result, not a storage throughput/latency claim; Letta is substantially broader than OpenViking's retrieval layer. |
| [Qdrant](https://github.com/qdrant/qdrant) | Rust | Apache-2.0 | Production vector database: dense/sparse/multivector search, filtered HNSW, payload indexes, quantization, sharding/replication, REST/gRPC; Qdrant Edge can run in-process | [Vendor benchmark](https://qdrant.tech/benchmarks/) says Qdrant had highest RPS and lowest latency in almost all tested 2024 scenarios, including a 4x RPS gain on one dataset. Qdrant itself warns its benchmark may favor Qdrant. It does not supply memory extraction, summaries, sessions, or hierarchical context logic. |
| [LanceDB OSS](https://docs.lancedb.com/faq/faq-oss) | Rust core; Python/TypeScript/Java bindings | Apache-2.0 | Embedded, in-process retrieval database on the Lance columnar format, with vector/full-text/hybrid search and object-storage support | [Official docs](https://docs.lancedb.com/enterprise) characterize OSS as single-process at 10–50 QPS and Enterprise as up to 10,000 QPS; these are product-tier claims, not agent-memory benchmarks. Docs also claim Lance random access is up to 1000x faster than Parquet. LanceDB does not supply the OpenViking semantic/session pipelines. |

## Interpretation

- Closest permissively licensed, self-hostable OpenViking substitutes: **Hindsight**, **Supermemory**, **Cognee**, and **Mem0**.
- Best existing Rust-first candidate: **Cognee-RS**. It is much closer to OpenViking than Qdrant/LanceDB, but is young; benchmark it on the intended workload before adopting it.
- Most convincing current quality/performance story: **Hindsight**, but it is Python and its primary persistence is PostgreSQL/pgvector.
- Qdrant and LanceDB are useful if building a smaller custom memory layer; they are not substitutes by themselves.
- Do not compare LoCoMo/BEAM scores with vector-query RPS. End-to-end latency is usually dominated by LLM extraction/reranking, embeddings, and network/model choice rather than whether orchestration code is Python or Rust.
