# Native Rust memory — engine contract

Status: native contract, boundary review 2026-09-08. **Owner: native Rust memory module.** The default host integration is an in-process Rust module boundary; the versioned HTTP API remains available for standalone deployments. The [native glossary](../memory/CONTEXT.md) owns vocabulary. The [service plan](agentic-memory-service-plan.md) owns scope.

Company roles, consent UX, publication review, offboarding policy and exports belong to the host application. Rust enforces admitted native operations and their invariants without importing those role names or running a second approval workflow.

## Recommendation and design review

The host owns prompt assembly, conversation continuity, human intent and provider checks. Native retrieval and processing details formerly mixed into it are consolidated below under [retrieval and derived processing](#retrieval-and-derived-processing). Accepted policy and the first-core security/lifecycle contract remain unchanged.

Build our own small **governed memory module**, not our own vector database, language model, agent runtime, or generic workflow engine. Its value is concentrating authorization, evidence, applicability, lifecycle, and bounded retrieval behind one interface used by HTTP, dashboard, and MCP adapters. The host still runs the agent and decides when to call the answer model.

For an AI using this module, the useful property is not “remember everything.” It is: get the right current evidence with little searching, know what is missing or disputed, and safely correct a remembered fact. Prefer an explicit missing result over a plausible guess presented as memory.

| Alternative | Judgment for this scope |
| --- | --- |
| Keep the former OpenViking integration | Rejected by ADR-0123; retained only as a design and optional benchmark reference |
| Thin Go module inside ConsultAI | Smallest implementation if independent Rust/open-source deployment is dropped; loses the requested independent product seam |
| Own Rust module over proven SQL/search primitives | Recommended for the user's standalone product goal; governance and integrations are real work, not a free performance win |
| Adopt a complete memory/agent stack | Can supply extraction/UI sooner, but still requires verifying our exact ACL, retention, source, and approval contract |
| Invent graph/planner/vector infrastructure | Defer; not justified by the current examples |

Borrow OpenViking's navigation/progressive detail, TencentDB's inspectable assets and bindings, Funes's exact evidence, and the working-set/temporal patterns in the strategy research. These are design references, not a license to copy implementations or a finding that our capabilities are unique. The file research records current source-specific differences.

The 2026-09-07 landscape review supports retaining this foundation. Its refinements below concern query preparation, context-preserving search representations and stronger evaluation; they are not delivered capabilities, a backend replacement or amendments to the fixed first-core contract.

### Decisions tightened by this review

- Hosted-first PostgreSQL rather than SQLite-first: the primary consumer is a multi-user web app already operating PostgreSQL. One database backend first; self-hosting initially includes PostgreSQL. Independent deployment does not require zero external processes.
- Full-text retrieval plus pgvector exact authorized search first; no separate search cluster, mandatory reranker, or recursive directory planner. Add approximate indexes only after a representative latency/recall test. pgvector documents exact search by default and a recall tradeoff for approximate indexes; filtering can leave ANN queries short of results, even with an iterative-scan limit. This is a recall issue to measure, not permission to return unauthorized rows. [pgvector documentation](https://github.com/pgvector/pgvector)
- One native deployment can serve HTTP and bounded durable processing when implemented; no dashboard or processing daemon is implied by the current router. Untrusted parsing needs a separate ephemeral sandbox, not merely a Rust worker thread. CPU/model work must not block request handling; network/model calls must not hold database transactions open.
- Start with tenant-scoped relational evidence links. They support provenance and invalidation without an ontology or graph database.
- No automatic promotion of private inferences to company knowledge, no silent positive source-permission cache, no AI publication approval, and no promise of operator secrecy.

## What is stored and what remains elsewhere

| Record | Minimum information / invariant |
| --- | --- |
| Collection | Tenant, stable ID, audience kind, owning user if private, grants, disclosure policy, authorization generation |
| Item | Tenant, collection, stable ID, kind, active revision, suspension/deletion generation |
| Revision | Immutable content or source handle, description, applicability, timestamps/known validity, provenance, verification, supersedes link |
| Derived representation | Exact source revision, parser/model/config version, chunk locator or summary/embedding, dependency IDs, processing state |
| Memory claim | Item revision plus subject and applicability; explicit assertion, tentative inference, or externally evidenced fact remain distinct |
| Admitted revision operation | Trusted host decision reference, exact target/base/input, native scope, stable operation identity and receipt; no native Company review inbox |
| Versioned instruction content (later) | Governed item/revision; host owns installation, activation and tool authority |
| Job | Tenant, operation ID, actor or durable delegated authority, input revisions/generations, attempt/lease, deadline, state |
| Audit / deletion marker | Sanitized operation metadata; immutable audit, monotonic deletion generation and purge status, no copied prompt/content |

Every tenant-owned relation carries a tenant key, including links, jobs and source records. Use tenant-qualified keys/references to prevent cross-tenant relationships, scoped uniqueness for idempotency, and service-generated identifiers. Do not expose constraint errors that reveal foreign records. PostgreSQL RLS is tenant defense in depth; owners/superusers/bypass roles and integrity-check side channels require care. Runtime uses a non-owner role without `BYPASSRLS`, distinct from migrations. The current API executes constrained `SECURITY DEFINER` functions with their owner's effective privileges; caller `NOBYPASSRLS` and table `FORCE RLS` do not prove that every nested query is subject to RLS. Explicit credential/tenant/resource checks, function grants, trusted search paths and restricted-runtime behavior tests remain the decisive boundary. Native collection checks belong here; Company and provider decisions belong to Go. [PostgreSQL row security](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)

ConsultAI owns its identities, permissions, business facts and uploaded originals; Go is the authority for those. Rust owns memory representations and indexing, and never reads Go's private tables or broad R2 credentials. Standalone tenants use the module's own grants with an established authentication integration. Do not build a new identity provider or maintain two editable sources of grants for a managed tenant.

Confirmed first-core order (user, 2026-09-06): standalone authority first, with its own identities and permissions; ConsultAI-managed integration later. Prove the core without ConsultAI or its private tables. Only native authority is in the prototype; the managed flows below remain later integration requirements. Authentication and the separate trusted-writer binding remain entry gates under [D01](agentic-memory-domain-review.md#d01--a-tenant-id-is-not-an-authority-and-a-service-credential-is-not-an-employee).

Host-held recent conversation is not another durable memory table. To save a private assertion, retain the explicitly authorized bounded evidence excerpt and source identifier when policy permits. A session ID that will expire is not a promise of a permanently reopenable transcript. Evidence may honestly be marked “user assertion; original conversation expired.” Connected-source transient text may not become such an excerpt under current ADR-0093.

## Agent read interface and turn flow

Rust returns bounded authorized evidence; the host decides skip/direct/search, assembles the prompt and runs the answer model. See the ConsultAI turn flow and complete dependency revalidation contract. A standalone host must provide equivalent behavior for a whole-agent guarantee.

### Retrieval policy, without an extra orchestration engine

The [native retrieval design](#retrieval-and-derived-processing) is canonical for hybrid eligibility, ranking, source detail and processing. Keep current-only semantics until a historical slice is supported. No search string, summary or match score authorizes a mutation or business action.

### Proposed HTTP contract

This table distinguishes current native routes from future contracts. The implementation/checklist remains authoritative for exact fields. Managed human confirmation, Company proposal submission/review and provider upload UI are Go routes, not native endpoint commitments.

| Operation | Native contract |
| --- | --- |
| `GET /v1/collections`, `GET /v1/items` | Current authorized pagination; opaque cursor, no global totals |
| `POST /v1/search` | Current bounded lexical/passage evidence plus optional generation-bound precomputed semantic query vectors; no native provider client |
| `GET /v1/items/{id}` | Current item read with optional expected item revision; no historical/section/representation selector in the core |
| `POST /v1/memories` | Trusted private create with exact content/applicability and idempotency key; agents cannot write |
| `PUT /v1/items/{id}` | Trusted exact correction with expected current revision; never upsert or similarity-retarget |
| `DELETE /v1/items/{id}` | Trusted exact forget; durable exclusion and safe receipt; no implicit independent-source deletion |
| Managed projection, admitted shared activation, complete dependency validation, ingestion/job status and scoped data transfer | Later versioned contracts; do not invent public routes or reuse private writer authority as a shortcut |

Automatic capture remains off. A model/document `confirmed` field cannot authorize a native write. Go authorizes the exact human decision; Rust still validates the authenticated operation, native scope, lifecycle and expected state.

Example `search` body: `{"query":"Cedar payment terms","scope":{"subjects":["sub_opaque"]},"max_context_bytes":2400}`. A subject ID is an untrusted narrowing selector resolved in the authenticated tenant and app namespace, not a grant. Do not accept tenant, employee, group membership, human confirmation, provider URL, or connection authority from model-written fields.

Current byte-only search envelope fields are `request_id`, `status`, `items`, `context_bytes`, `truncated`, and `warnings`; token-budget requests additionally return the counted `context` described under native budgets. Exact item fields are defined in the implemented schema. Passage citations identify the source revision, extraction set, passage and server-owned locator in addition to item/revision identity. Richer verification, conflict, applicability explanations and semantic hit reasons are proposed additions, not existing response guarantees. Rank is not truth confidence. Native responses expose no authorization generation or epoch as client authority; receipts require current authorization on reuse.

Explicit stale feedback: clients retain item/revision references for plain item content. Document/derived evidence also requires exact source, active extraction-set and representation dependencies; an unchanged item revision is insufficient after reprocessing. The internal `eligible_source_passages` primitive checks the stronger source/set identities, but a complete authenticated host-facing dependency operation remains an integration gate. Revalidate the relevant identity before reusing evidence. An expected-current-revision mismatch returns a machine-readable `stale_context` conflict only while the caller remains authorized; it does not silently substitute new content. The client reloads permitted current evidence and recomputes affected work rather than relabelling old output with a new revision. Missing, forgotten, withdrawn or inaccessible targets use the same non-enumerating unavailable response; a previous receipt does not authorize disclosure of their current state. Hosts recheck before the next model request and before releasing dependent results or executing dependent actions. First core uses HTTP revalidation, not a notification bus or push subscription; an already-running model request cannot have its input recalled, but a cooperating host discards/recomputes its unreleased stale result. The native serialization and in-flight limit are fixed below.

Use `200` for completed reads (including an honestly empty result), `201` for durably created records, `202` for accepted asynchronous processing, `409` for a known authorized stale revision/idempotency conflict, `429` with bounded retry guidance for limits, and `503` when required processing/authorization is unavailable. Use the same non-enumerating response for missing and forbidden item identifiers. `degraded` indicates an optional retrieval capability failed; never turn an authorization failure into an unscoped fallback. Job status/errors are also tenant- and actor-authorized, with no parser-output leakage.

Managed tenants accept authenticated Go traffic only, bound to the deployment and intended Rust recipient; never trust a self-reported service-name header. The application protocol is the existing versioned HTTP/JSON API. An authenticated host envelope contains a short deadline and request/operation identity plus narrowing scope. ADR-0127 fixes the managed identity bindings, Go-owned translation, native ACL projection, acknowledgement, and fail-closed revocation direction; the concrete workload-authentication mechanism and distributed race tests remain implementation gates. These do not require inventing custom signed tokens or replacing HTTP with JSON-RPC/gRPC. Native dashboard sessions require ordinary CSRF/session protections; remote MCP must follow the selected protocol's authentication, not assume every CLI understands custom headers.

### First-core native contract — implementation entry

This section resolves the routine engineering choices in D01–D05/D09 for the standalone synthetic prototype only. It does not define ConsultAI-managed impersonation, shared publication, dynamic administration, business-policy execution, production retention or a new identity provider.

#### Identity, credentials and trusted setup

- A native `tenant_id` maps one-to-one to a future ConsultAI Company; a human `principal_id` maps to an Employee, and an `automation` principal maps to an Automation Principal. An `app_id` identifies the registered calling application, not a person and never an authority to impersonate one. All are service-generated opaque 128-bit identifiers, qualified by tenant; display names and emails are labels only and never merge identities.
- The prototype uses one authentication mechanism: a 256-bit random opaque bearer credential sent over TLS in `Authorization: Bearer`. Only a SHA-256 digest and a non-secret credential ID are stored. A credential is immutably bound at issuance to one tenant, principal, app, credential class, allowed operation set, `issued_at`, mandatory `expires_at` (at most 24 hours in fixtures), and optional `revoked_at`. Missing, expired, revoked or mismatched credentials fail before body-controlled scope is considered. Rotation issues a new credential and revokes the old one; no refresh, delegated impersonation or caller-selected authority mode exists.
- There are exactly two non-overlapping credential classes. `agent_reader` can call only `list`, `search` and current `read`. `trusted_writer` can call only private create, exact correction and exact forget for its bound human principal. Possessing both requires two credentials and two explicit client configurations; operation-set overlap is rejected at setup and at request authorization.
- Trusted setup is an operator-run, one-shot headless command using the separate migration/setup database role. It loads a checked-in synthetic manifest of tenants, principals, apps, private collections, seeded shared collections and fixed grants, then prints each test credential once. The runtime role cannot issue credentials or edit grants. The prototype has no signup, login UI, dynamic admin endpoint, group mutation, live shared publication or managed mode.
- The trusted writer client, not the model, constructs the complete write request after a direct test/user action. The authenticated request itself binds the exact content and applicability for create/correction or the exact item/current revision for correction/forget. The service computes a canonical payload digest and binds it to the idempotency record; a changed payload under the same key conflicts. It accepts no `confirmed`, `user_confirmed`, actor, tenant or audience field. The headless acceptance caller is a deterministic HTTP test process with the writer credential in its process environment; the manipulated-agent fixture receives only the reader credential. This proves boundary enforcement without a dashboard and is not a reusable human-presence protocol.

#### Opaque subjects and current-time semantics

- Every applicability reference is a service-created `subject_id` with immutable kind `principal`, `app`, `customer` or `project`. Principal subjects resolve to a native principal. App subjects resolve to an app. Customer and project subjects are created during trusted setup under exactly one `app_id`, so equal external names in two apps are distinct. Names, emails and model strings never resolve or create a subject during a memory operation.
- A private memory must name at least one subject. If it names a `principal` subject, that subject must be the trusted-writer credential's bound principal; another principal is invalid even if the caller can guess its ID. A user preference normally names that bound principal subject; customer/project facts use their app-namespaced subject and may additionally name the app subject. An omitted, unknown, wrong-kind or cross-app subject is a schema/scope error, never an empty filter or tenant-wide fact. Company-wide applicability is not representable in first-core writes; shared fixtures are seeded explicitly.
- The authenticated principal and credential-bound app subjects are always implicit in a search context. Caller-supplied customer/project subjects may only narrow that context and must belong to the bound app. Matching is conjunctive across subject kinds and alternative within one kind: for every kind present on a revision, at least one stored subject of that kind must equal a context subject; extra context kinds do not disqualify an item. Thus an app + Cedar + Renewal item requires all three kinds, while two project subjects on one item mean either project. Requiring two simultaneous subjects of the same kind is unsupported in the first core.
- Omitting `scope.subjects` searches only items applicable to the implicit bound principal/app context; it does not range over every customer/project the caller might otherwise read. An explicit Cedar scope can additionally match Cedar items and app-wide/principal items, but not another customer, another project required by the item, or an equal label under another app. Unknown or empty explicit subject lists are rejected rather than treated as omitted.
- Each revision stores server-assigned `recorded_at` (the transaction time at which the service first knew the assertion) plus optional writer-supplied `valid_from` and exclusive `valid_until`. Both validity values must be RFC 3339 UTC instants and `valid_from < valid_until` when both exist. Omission means unknown, not forever or company-wide. Observation time does not verify the claim or prove it was known before `recorded_at`.
- First-core retrieval supports only `time_mode: "current"` (the default): active current revisions whose known validity contains the request transaction time, plus revisions with unknown validity clearly labelled `validity_status: "unknown"`. It never returns superseded revisions. `valid_on`, `known_as_of`, explicit historical revision reads and other historical reconstruction return `422 unsupported_time_semantics`; the service does not infer a historical answer from today's state.

#### Serialization, in-flight limit and jobs

- Native tenants have one PostgreSQL `authority_epoch` row. Every write request, including a possible idempotency replay, uses a `READ COMMITTED` transaction and locks in this order: tenant authority row `FOR UPDATE`; scoped idempotency row/key; target item rows in ascending opaque ID; then dependent job/representation rows in ascending ID. Credential/grant revocation, source withdrawal, item correction/forget and job commit use the same order, incrementing the epoch when authority/serving state changes and committing with their audit record. No path acquires an item/idempotency lock before the tenant row.
- Preliminary token parsing may reject obviously invalid requests, but it is not mutation authorization. After acquiring the tenant lock—and therefore after any wait—every new mutation uses fresh `READ COMMITTED` statement snapshots to read the credential, principal, app, private ownership/grants, target lifecycle and expected revision; no pre-lock authority result is reused. Credential expiry is evaluated against PostgreSQL `clock_timestamp()` obtained after lock acquisition, not request arrival or transaction-start time. Only then may it execute. This per-tenant serialization point supplies the total order and is intentionally a prototype-wide tenant lock, to be split only after measured contention.
- Reads/searches may do bounded work outside a transaction, but immediately before disclosure they start a short `READ COMMITTED` transaction, lock the tenant epoch `FOR SHARE`, then freshly check the credential against the post-lock database clock, principal, grant, audience, item/revision, withdrawal and deletion state before materializing the bounded response and recording its release decision. A revocation/withdrawal committed first therefore denies; a release decision ordered first may finish sending its already-authorized bytes. Bytes already released, a model request already dispatched, and information already delivered cannot be recalled.
- A cooperating host retains only returned opaque item/revision references. It revalidates those references through authenticated current `read` before model dispatch, before every later model request, and before releasing dependent output; no raw authority epoch or generation leaves the service. `409 stale_context` is returned only to a still-authorized caller whose expected revision changed; missing, forgotten, withdrawn, revoked or inaccessible targets return the same non-enumerating `404 unavailable`. The host discards unreleased dependent output and rebuilds from fresh permitted evidence. There is no push invalidation and arbitrary clients outside this protocol receive no whole-agent guarantee.
- A private write atomically creates at most one durable job authority record containing tenant, purpose, operation ID, principal provenance, exact input item/revision, authority/deletion/consent generations, pipeline version and deadline. It contains no bearer credential and grants no general read. Private jobs remain valid only while the principal is active, owns the private collection, consent/generations match and the item is current. Shared live processing is absent; seeded shared fixtures are already lexical-ready and have no reusable submitter authority.
- Jobs are at-least-once with a unique key over tenant, purpose, operation, input revision, generation and pipeline version. At most one worker may hold a 30-second lease; a job gets at most three attempts and a ten-minute deadline. Transient failures retry within both bounds. Invalid input is terminal `failed`; changed revision/generation, withdrawal/deletion or lost authority is terminal `stopped_stale` and never blindly retried. Before sensitive work and again in the same tenant/item-locked transaction as result commit, the worker rechecks every authority/input field. Commit is idempotent; lease expiry cannot duplicate activation, and retry requires the immutable original input or a new authorized operation.

#### Bounded native HTTP schemas and durable records

- JSON request bodies are UTF-8 and at most 64 KiB for writes and 16 KiB otherwise, with at most 16 nesting levels and 256 object members/array elements. Duplicate keys, unknown fields, unknown enum values, invalid UTF-8, non-integer numeric values and trailing data are rejected. IDs are opaque strings of at most 64 ASCII characters; idempotency keys are 16–128 ASCII characters; cursors are at most 512 bytes and bind tenant, principal, app, operation, scope and a 15-minute expiry.
- `list` uses `limit` 1–100 (default 20) and returns no total. `search.query` is 1–4,096 UTF-8 bytes, accepts at most eight subject IDs, `max_context_bytes` from 1 through the configured operator maximum (see native budgets), and returns at most 12 items. `read` returns current content only in the core and accepts an optional expected current revision. Memory content is 1–32 KiB UTF-8; applicability accepts at most eight subjects. Create rejects item/revision targets; correction and forget require the path item plus exact expected current revision and never create or retarget.
- `Idempotency-Key` is mandatory for writes and scoped to tenant, principal, app and operation family. The first committed operation stores the canonical method/path/body digest, completion outcome and safe receipt fields for 24 hours in the existing idempotency record. The unique scoped key serializes concurrent duplicates, so exactly one request may execute the domain mutation and append its mutation audit, with at most one applicable job; replay creates none of them again.
- Every write performs its decisive checks only after taking the tenant lock in the order above: validate the credential/principal/app against the post-wait database clock and current operation permission, then look up that scoped key. No matching completed record means this is a new mutation: perform all current target/ownership/grant/lifecycle checks, including correction/forget's expected base revision. A matching completed record means replay, not mutation: require the identical canonical request and current authority to disclose that operation's receipt, but do **not** recheck the original expected base revision or execute the domain mutation. A different canonical request returns `409 idempotency_conflict`; failed pre-commit attempts do not reserve a key.
- A replay receipt proves only that the identified operation committed at `completed_at`; it never claims that its resulting revision is still current and grants no content/history access. Receipt-disclosure authority means the same bound principal/app is active and its current `trusted_writer` permission still covers the operation family and private collection recorded in the idempotency record; it does not require the target or old base revision to remain current. With that authority, return the original safe receipt with `replayed: true`. If a later correction changed current state, the receipt remains the historical operation receipt without current-state fields. If the operation or a later operation forgot the target, return only `operation_id`, operation kind, `completed_at` and `replayed`, omitting target/revision details. If the credential/principal or relevant collection/receipt authority is now revoked, return the normal `401` or non-enumerating `404 unavailable` and disclose no receipt. A prior receipt never bypasses a current read, target or content check.
- Statuses are bounded enums: operation `ready`, `degraded`, `pending`, `failed`, `stopped_stale`, `unavailable`; semantic readiness `not_requested`, `pending`, `ready`, `failed`. A committed private save is `ready` only after its current lexical representation is in the same transaction; semantic state is separate. `200` covers completed reads/deletes and authenticated replay receipts, `201` first create, `202` accepted optional job, `400` malformed schema, `401` credential failure, `404` the normalized missing/forbidden/deleted/withdrawn target or undisclosable receipt, `409` authorized stale/idempotency conflict, `422` unsupported time semantics, `429` bounded admission with `Retry-After` 1–60 seconds, and `503` required authorization/storage unavailability. Errors contain only `request_id`, `status`, stable `code` and safe field name when schema-invalid.
- Internal operation errors are private typed `std::error::Error` values. They retain lower-level database, timeout and body-read sources for inspection by trusted code without formatting `Display`, `Debug` or the source chain into HTTP, audit rows or logs. A PostgreSQL `42501` from the constrained current-authority checks remains a distinct source-bearing credential failure mapped to sanitized `401`; other required-storage failures map to sanitized `503`. Best-effort rejection-audit failures also retain a typed database source internally but never replace the original public response and are not speculatively logged.
- The local audit row contains time, request/operation ID, tenant, principal, app, non-secret credential ID, operation kind, opaque target ID when known, outcome/status, authority epoch and idempotency-key digest. It excludes bearer tokens, content, query text, excerpts, subject labels, evidence, payload digests, response bodies and raw errors. Audit is committed with native mutations; rejected requests and receipt replays append only the sanitized fields established for that attempt. A replay never appends a second mutation audit.
- Forget commits immediate serving exclusion: it clears the active pointer, increments deletion/authority generations, makes all revisions and derivatives ineligible, stops matching jobs, writes audit and creates a minimal deletion marker in one transaction. The marker contains only tenant/item IDs, deletion generation/time, operation ID and purge state; no content, subjects, labels, revision body or embedding remains in it. Physical purge is asynchronous cleanup and cannot restore serving eligibility. The prototype retains the marker while any fixture snapshot can be replayed and makes no deadline or backup-erasure promise; production purge, backup expiry and recovery-ledger retention remain D09 release decisions.
- Grants are the fixed synthetic setup records. The core evaluates memory authorization only; it does not assign mandatory business policy, approve an exception, authorize an external action or execute business-policy rules. Policy-ignoring-agent tests belong to the later host/action slice, while the core continues to treat every claim and instruction as untrusted data.

### Hostile prompts and malformed requests — mandatory security contract

User requirement clarified: protected company, department and personal data must remain inaccessible even when a prompt, uploaded document, installed skill or model-generated tool call is malicious. We assume the model can be manipulated; model refusal is not the authorization boundary. This requirement applies inside memory itself, as well as at the managed Go adapter.

- **Separate text from authority.** Treat queries, extracted text, citations, skill instructions and model outputs as untrusted data. They cannot set the authenticated actor, widen the response audience, grant permissions, confirm human intent, or switch a tenant into standalone mode. An ordinary authorized search string may contain hostile instructions; it remains search data, not executable policy.
- **Reject malformed operation envelopes.** Validate the versioned request schema at each entry point: required fields, allowed fields/enums, exact types, identifier syntax, lengths, nesting, numeric bounds and body size. Reject duplicate JSON keys and conflicting identity information rather than allowing different parsers to choose different values. An invalid/unknown scope must not become an omitted filter or global search. Rejection occurs before sensitive retrieval, mutation or content-bearing model calls.
- **No raw execution authority.** Use parameterized database queries and allowlisted operations/filter fields. Never interpret model text as SQL, a shell command, a storage key, a server filesystem path or an arbitrary fetch URL. Resolve resource selectors to an exact tenant-owned item through the authorized operation; guessing an ID or encoding a path does not grant access.
- **Enforce on every route.** HTTP, dashboard, MCP, background jobs, history, downloads and export/import enter the same authorization implementation. Scoped handles/cursors bind to principal, tenant, operation and expiry, and are reauthorized on use. An authenticated app credential alone must not allow arbitrary employee impersonation. Agents have no grant-management, migration, database-admin or human-review credentials.
- **Prevent cross-request contamination.** Tenant/principal context stays request-local; pooled database connections use transaction-local identity with safe failure cleanup. Shared mutable agent state, result buffers, context assembly and diagnostics must not carry one user's data into another request. Retained derived data must preserve source ownership and disclosure policy.
- **Contain a manipulated agent.** Even if the AI requests protected payroll after reading an injected document, the server denies that operation before revealing content or metadata. Authorized content must also obey audience/egress rules: the host cannot give the model an unrestricted outbound tool that bypasses those rules. Content labels and prompt-injection detectors may help answer quality, but cannot replace these controls or establish user consent.
- **Fail closed, with bounded work.** Missing identity, ambiguous resource resolution, stale authority or unavailable mandatory checks deny the affected operation. No emergency unscoped fallback. Apply request/job limits and sanitized audit; do not put rejected payloads or secrets in logs.

These are falsifiable implementation requirements, not a claim that prompt injection is solved. The model may still produce a misleading answer from material it is permitted to see; ACL is meant to prevent that manipulation from becoming unauthorized access or action. Compromise of trusted Go, the running memory process or privileged operators is a different threat from hostile prompts and requires the documented least-privilege/deployment controls. Release must be blocked by any observed authorization bypass; require adversarial review of the implemented paths before claiming strong protection.

### Initial budgets to validate, not speed promises

Rust owns per-request input, candidate, excerpt/response, SQL and processing bounds. Go owns whole-prompt tokens, model output reservation and cross-call turn budgets; see host budgets. A 4,096-byte excerpt limit is not a 4,096-token model budget and a top-k result limit does not bound query-plan work. Proposed native tuning and overload gates are below.

## Writes, consistency, and revocation

Private explicit write: validate authority/input → commit immutable revision, current lexical representation, active pointer, audit and job record atomically → acknowledge durable save → derive optional representations. Confirmed readiness rule: after save, authorized direct reads and keyword search see the current revision, including fresh-session search without its ID. Semantic indexing reports pending/failed/ready separately; never use an old revision's excerpt/vector as current or imply complete semantic coverage while authorized indexing is pending. Keyword readiness does not guarantee every paraphrase matches. Confirmed correction rule: require the exact authorized item ID and expected current revision, checked atomically with the write. Reject a stale edit without mutation for review against the current version; no automatic merge, retargeted retry or similarity-based overwrite. AI match suggestions do not replace D02's trusted user-controlled authorization. Private auto-capture defaults off; turning it off increments a consent generation and prevents queued capture from committing. Store no hidden durable backlog of entire conversations.

Capture/extraction admission is a host responsibility: exact user intent, permitted content, destination and source retention must be established before a trusted native write. Native candidate/derived processing must retain exact inputs, consent/authority generations and lifecycle checks; it cannot turn an inferred assertion into verified Company policy. The host design owns suggestion, human review and capture policy. Automatic capture remains off.

External origin provenance is not necessarily an active serving dependency. ConsultAI's approved snapshot policy admits an independent governed item; its derivatives depend on that saved item's native revision/lifecycle, not continuing provider access. Only trusted admission may establish that distinction. The managed representation/write path is not implemented, and this policy does not weaken current native document-source withdrawal or exact extraction-set checks.

Shared publication is Go-owned for managed tenants. Rust validates and stages the exact admitted revision, then activates only complete required source/citation/lexical representations under current native authority. It must not activate a stale or suspended host decision or infer a reviewer from a role name. Go keeps approval and readiness distinct through the durable decision/receipt contract; optional vectors/summaries have separate readiness.

Jobs are at-least-once, keyed by tenant, operation, input revision, generation and pipeline version. Commit durable processing intent with the mutation instead of adding a message broker. Claim jobs with bounded leases, retry within a deadline, and make completed writes idempotent. Before committing derived content, compare revision, deletion and consent generations and recheck the principal's current authority. Obsolete jobs stop; a lease timeout alone cannot duplicate activation. Processing success or failure cannot manufacture host verification or approval.

Jobs revalidate before sensitive work and atomically with result commit. Obsolete input produces an explicit stopped/stale outcome in authorized job status, not silent success or blind retry. Detailed reasons and replacement revision IDs require current disclosure authority; otherwise return a non-enumerating unavailable outcome. A replacement job requires fresh authorized inputs; a forgotten item cannot be recreated by the old operation.

For ConsultAI-managed changes, Go remains authoritative for the human decision and its platform audit; Rust owns the revision/projection result and its local audit. These databases do not share an atomic transaction. Go first commits the authorized decision plus durable operation intent, then sends the stable operation ID/base revision to Rust. Rust validates current authority and base state, commits its result atomically with local audit, and returns an idempotent receipt. Go records completion only after a confirmed receipt; timeout leaves pending reconciliation, not a false rollback or a second publication. Queries must honor both current Go approval/suspension and Rust readiness. Native tenants keep these transitions in the one memory database.

Blob writes and SQL are not one transaction. Stage immutable bytes with tenant ownership and a digest; publish a reference only after the object is complete and verified. Failed SQL commits leave quarantined unreferenced objects for bounded cleanup, never active broken references. Do not deduplicate across tenants in a way that exposes content existence. Cleanup must not remove a referenced object or race an authorized upload commit.

Derived records carry exact source-revision dependencies and never a broader audience/egress policy. Cross-collection summaries are deferred; compose authorized snippets per request instead. ADR-0124's explicit, differently reviewed publication of Employee-selected private text is a new independent shared item, not an automatic derived representation; it exposes neither the private original nor its protected provenance. Confirmed distinction: loss of a reader's effective access excludes that source and its derivatives for that reader, without disabling valid knowledge for other authorized readers. Source withdrawal/suspension/deletion excludes dependent representations for all readers at read time, cancels stale jobs, and requires rebuilding or suspending affected claims; asynchronous vector deletion is cleanup, not the security control. Independent valid support may justify later re-verification, not automatic truth. The native ordering and job-authority details are fixed in the first-core contract above; managed distributed ordering remains later work.

Managed authorization is checked before internal query and again immediately before each external disclosure: model embedding/reranking, prompt construction, client output, download, or export release. Rust must not send managed candidates to an external model before Go establishes current authority; use Go's narrow model route for content-bearing work. Generation stamps cheaply detect staleness but do not replace applicable live Gatekeeper checks for source-bound evidence. Independently admitted snapshots instead require their current native/host Context authority. Treat metadata search as sensitive too.

Revocation's honest guarantee is: decisions ordered after a committed revocation must deny; an already authorized in-flight disclosure or information already delivered cannot be recalled. Native operations use the first-core tenant serialization point above; managed Go/Rust/source checks still have a distributed race window that must be specified and race-tested later. Do not claim instant global revocation from asynchronous invalidation. On a changed membership/response audience, the host rebuilds context from retained permitted evidence; untraceable mixed summaries or transcript segments are discarded, not blindly replayed. Downstream third-party clients must honor this contract for the guarantee to extend beyond our module.

### Department confidentiality and model egress

Native collections express audiences, not business departments. Go owns Company Owner and delegated administration policy and projects effective native access. A native manager's ability to alter grants is security-sensitive, not implicit content read or protection from privileged operators.

Derived content cannot widen source disclosure policy. Local-only input cannot reach remote embedding, reranking, extraction, answer or diagnostic services. Managed content-bearing inference passes through Go's narrow authorized model route; standalone deployments enforce the equivalent configured native boundary. No provider credentials go into normalized source text, job input or model prompts.

## Files and other resources

Files are first-class sources, not text pasted into a preference memory. A document item retains an immutable original reference, extracted text with source locators, optional description/summary, and chunks/embeddings. Memories may cite permitted source revisions without duplicating whole documents. Source title/path/thumbnail and original download are protected exactly like the content.

The current database foundation represents exactly one immutable source identity per document item revision, parser/config-versioned extraction sets, and bounded ordered source passages. Passage eligibility has no independent ACL: an internal selector first reuses the exact current-revision, collection, credential, applicability, withdrawal and deletion checks of the item read path, then requires the caller's expected source and extraction-set identities before returning 1–16 named passages. An authorized stale identity fails explicitly rather than substituting content from a newer set; an authorized item with no active extraction remains unavailable. A trusted internal activation validates and indexes the complete set before atomically switching the active pointer under the tenant authority lock; failure preserves the prior pointer, while success advances the authority epoch. Because this ingestion boundary has no authenticated end-user mutation identity, it does not fabricate a `mutation_audit` row; job/operator audit identity is still required when a production ingestion caller is introduced. This is relational lifecycle and authorized search support, not a public upload, parser, or original-object store.

Office-first scope confirmed 2026-09-06: PDF, Word (`.docx`), Excel (`.xlsx`), CSV and PowerPoint (`.pptx`) are primary ingestion/evaluation targets, not optional formats inferred from a plain-text benchmark. Implement incrementally; no production upload/parser support is claimed by the current API. Search returns direct passages from complete extraction sets activated through the trusted internal operation, then may append only immediate, same-parent passages connected by reciprocal continuation metadata within the exact governed source and active set. The office-document pilot records per-format extraction/citation contracts, an office-heavy synthetic corpus, coverage failures and measurements before optimization.

Never execute document content or let a parser follow a host filesystem path.

Originals for managed ConsultAI uploads stay in R2; Go provides only narrowly authorized job input. Standalone uses its immutable volume. Binary live references use transient parsing without persistent artifacts. Render previews as escaped content or separately sandboxed viewers; no active HTML/macros/scripts.

Preserve page/paragraph/row offsets back to the exact source revision. Oversized tables return a warning/bounded excerpt, not a silent assertion of completeness. Test these parameters on real format fixtures and table questions; no universal chunk size is claimed.

The synthetic office policy comparison selected reciprocal continuation-aware expansion over direct-only, unconditional ±1 and small overlap because it recovered the one authored split with less irrelevant evidence. Search now applies that policy automatically after direct results: expansion stays within the exact item revision, source revision, active extraction set and structural parent, preserves direct relevance order, and shares the aggregate byte and result/source caps. A warning about a bounded retrieval excerpt is distinct from incomplete ingestion, which must not activate. Define hidden/review-content coverage before enabling each parser. Store optional generated summaries separately as revision-bound, permission-inheriting navigation aids; source changes/deletion invalidate their serving eligibility. Benchmark extraction fidelity, retrieval/citation quality, parsing/indexing cost and search-plus-expansion latency per format, under the same total context budget. Calculate spreadsheet aggregates through a separately tested structured path, not a handful of retrieved rows or a generated summary.

`list` discovers authorized collections/items and `search` finds passages. A future bounded source-detail operation can expand exact evidence; `read(section)` is not a current public endpoint. Hosts admit edits through the appropriate trusted revision operation, with Company proposal review outside Rust. These are governed virtual records, not unrestricted filesystem access. Original PDFs/DOCX are immutable: an annotation/new revision must not pretend the original binary changed.

## Ownership, export, and import

Rust owns native serialization, tenant-qualified identity, exact revision/dependency integrity, bounded import validation and deletion/non-resurrection enforcement. Go owns the ConsultAI export/offboarding workflow, including who may export, reauthentication, review, 24-hour artifact lifetime and Employee recovery policy. Those business rules are not standalone native defaults.

Distinguish an ordinary content export from privileged full-tenant relocation. A content package may include authorized items, readable representations and permitted provenance; it does not implicitly include grant lists, group memberships, private-source inventories or operational authority records. A separately admitted relocation manifest may include necessary identity/grant mappings, but they remain inactive until destination authority is established.

Proposed native package format: versioned manifest, permitted JSONL/Markdown content, exact source locators and checksums, allowed immutable originals and non-content deletion evidence. Embeddings are optional rebuildable optimization data with their model/version/dimensions. Never include credentials, bearer tokens, raw errors or policy-prohibited connected bodies. An omission report must not reveal hidden sources or counts.

Take a consistent included-revision snapshot and immutable blobs; recheck current native eligibility during generation and release. The host handles intended-recipient/source checks and authenticated artifact delivery. Revocation can stop remaining transfer when detected, not recall delivered bytes. Export is not authority to bypass source or collection policy.

Import starts in bounded non-executing quarantine: verify package version, checksums, types, paths, symlinks, size and entry counts; resolve explicit destination identities and dry-run before active state. Reject unknown schema versions and never overwrite active records implicitly. Foreign verification/approval is provenance, not destination authority. Use stable operation/item mappings for retries, activate only admitted complete data, and separately report semantic readiness.

Restoration must replay authoritative deletion/revocation evidence before serving. A pre-deletion backup alone cannot establish current permission or resurrect a forgotten item. Full relocation, backup retention, production purge deadlines, operator custody and real restore proof remain release gates. Do not transplant ConsultAI's 12-month audit or 30-day offboarding rules into every native installation.

Standard companies share runtime/database infrastructure under tenant isolation and per-collection ACL. Apply per-tenant ingestion, storage, model-spend and request quotas to contain noisy neighbors. A Company or department must not choose infrastructure by supplying an arbitrary connection string/path. Private volumes, internal database access and scoped delivery remain operator-controlled.

Offer dedicated/self-hosted deployments using the same release and data format, with separate runtime, database, originals, credentials and backups. Dedicated VM/container/database is not necessarily dedicated physical hardware; specify the actual purchased isolation. ## Promising hypotheses and their rejection tests

1. **Evidence packets beat a memory text dump.** Small scoped excerpts plus known conflicts/source dates may improve grounded answers at the same context budget. Reject if they add tokens without improving the paired held-out outcomes.
2. **Remember exceptions as scoped facts, not global profile edits.** Customer/project applicability plus explicit correction may reduce damaging stale/wrong-scope recall. Reject the automatic inference path if it cannot reliably distinguish scope; keep user-confirmed fields.
3. **Cheap routes first, evidence-driven expansion second.** Skip/direct/hybrid before optional rewriting may avoid needless model calls while preserving hard-question recall. Reject if missed retrieval outweighs saved latency; expand only failing route classes.
4. **Authority follows evidence through the whole lifecycle.** Dependency checks, disclosure policies and export controls aim to make memory safer for business teams. This is an acceptance requirement, not a quality trade that can be switched off for a benchmark win.

No self-improving learning loop, automatic ontology, autonomous dreaming worker or adaptive policy engine is required to test these ideas. Improve prompts/chunking/routes using versioned offline evaluations first. A single fact's retrieval success is not permission to retain more user history.

## Retrieval and derived processing

### Eligibility comes before relevance

Both lexical and semantic result sets must satisfy tenant, bound app/principal, current collection access, task applicability, item activity, exact current revision, validity, withdrawal/deletion, and active extraction-set constraints. Current-only semantics remain the default; historical modes remain rejected until a separately tested slice supports them.

Each branch selects its top candidates from eligible records. Do not retrieve a global top-k and then use application filtering as the tenant boundary. An approximate index may internally visit other records; no such visited record becomes a returned candidate, model input, title, count, or public diagnostic. Restrictive filters can reduce approximate-search recall and must be benchmarked.

Managed results additionally pass the host's current source/recipient/egress checks; see the host boundary. Native eligibility never grants provider access or permits a model call before that check.

### Two complementary candidate sets

- **Lexical:** retain PostgreSQL full-text search and exact ID/read routes. The current `simple` text-search configuration supplies a baseline; it is not BM25, multilingual semantic understanding, or an automatic synonym dictionary. Evaluate language-specific tokenization and exact identifier handling with real test languages.
- **Semantic:** embed each eligible representation when its revision is processed, then embed the authorized search query with the same model/input conventions. Search vectors for similar meaning. Reuse stored embeddings across queries while their exact source version remains eligible; do not re-embed the whole corpus per turn.
- **Hybrid:** take the union of the lexical and semantic candidate sets. Requiring a keyword match in the vector branch would lose the paraphrases this feature is meant to recover.

Start with exact pgvector search over the eligible set and indexed relational filters. This is straightforward to compare against ground truth; it is not an unlimited-scale performance claim. [pgvector documents](https://github.com/pgvector/pgvector#filtering) approximate filtering behavior and [hybrid search](https://github.com/pgvector/pgvector#hybrid-search) with PostgreSQL full-text search.

An embedding captures similarity, not truth, negation, contractual approval, or entity identity. “Refund approved” and “refund not approved” may be close. Retrieval must preserve the exact source statement and its verification/applicability metadata; business actions still use the host's authoritative rules.

### Query preparation and context-preserving representations

**Versioned lexical query matching:** omitting `query_mode` preserves the existing `bounded-question-v1` preparation and explicit search syntax. Lexical-only requests may opt into `query_mode: "disjunctive_v2"`, which combines existing PostgreSQL simple lexemes as alternatives and keeps paired curly-quoted entity names as phrase units. ASCII quoted phrases, standalone case-insensitive `OR`, and exclusion syntax retain their original behavior. Existing Chinese tokenizer chunks remain intact. This mode rejects semantic search inputs; it does not rewrite embedding queries or change authority, ranking, result limits or context budgets.

Lexical-only `query_mode: "disjunctive_v3"` carries the same intended predicate as a native `tsquery`, avoiding v2’s compound-lexeme serialization fallback. Both modes keep the same tokenization and explicit-syntax contract. The legacy, v2 and v3 entry points use one private search core; the default and hybrid behavior remains unchanged.

Preparation falls back to the original v1 predicate with `lexical_disjunction_fallback` in the existing warnings array when generic syntax/bounds fail; v2 also requires a predicate round-trip check. It never creates an unfiltered scan. This opt-in is a measured development candidate, not a general relevance guarantee; see the longer-source comparison. Ranking cannot recover candidates excluded by the query predicate.

Treat candidate matching and scoring as separate choices. For the next retrieval slice, compare the existing query with bounded lexical preparation on natural questions, phrases, exact codes, abbreviations and supported languages. Preserve the original question for semantic retrieval; a focused lexical expression need not be the embedding input. Do not silently drop negation, dates, identifiers or explicit search operators. An empty/unsupported prepared query must not become an unfiltered corpus scan. Version and test changed query semantics before changing the current public contract. Native preparation is bounded parsing; optional model-assisted conversational rewriting belongs to Go and cannot alter authenticated scope or applicability.

Keep PostgreSQL FTS as the shipped control and include a **real BM25** challenger in the evaluation; `ts_rank_cd` is another PostgreSQL ranking function, not BM25. First improve candidate coverage, then compare ranking under the same corpus, permissions and evidence budget. Adopting an extension requires separate proof of deployment/version support, transactional revision visibility, restricted-role/definer behavior, filtering, backup/upgrade compatibility and operational cost. No extension or second search service is selected by this review.

For document indexing, distinguish **search representation** from **returned evidence** using the existing Derived Representation model:

- Start with bounded deterministic enrichment from the same admitted source: permitted document title, heading ancestry, sheet/slide label and relevant table headers alongside the passage. A title repeated on every passage must not dominate passage relevance; keep field origin explicit and compare weighting on development data.
- Bind enrichment to its exact item/source/Extraction Set, structural inputs and processing recipe. Do not borrow another collection's description, a hidden sibling, a future revision or an unretained conversation. A changed heading or title invalidates dependent representations even if the passage body is unchanged.
- Return original passage text and exact source locators. Any surrounding source text used to support the answer must itself be supplied as authorized, attributable evidence within the byte budget. Generated contextual descriptions, keywords and hypothetical answers are search aids, not quotations or independent proof.
- Use optional generated contextualization only if deterministic structure leaves a measured gap. Validate its output, count preparation/reprocessing cost, enforce egress and input limits, and retain direct original-passage retrieval. Never replace source evidence with extracted atomic facts or summaries alone.

These are indexing improvements, not permission to retain additional data. The existing source/passages and continuation policy remain unchanged. [Contextual retrieval](https://www.anthropic.com/engineering/contextual-retrieval) motivates the experiment, but its reported gains do not establish ours. A small preference needs no document-enrichment pipeline.

### Ranking and evidence selection

Use the engine plan's initial equal-weight Reciprocal Rank Fusion: `score(d) = sum(1 / (60 + rank(d)))` over the lists containing the candidate. Ranks begin at one; absent candidates contribute zero. Use stable scoped identity to break ties. Avoid adding raw lexical and cosine scores, which have unrelated scales. RRF-60 is a baseline, not a permanent optimum; a calibrated weighted alternative may replace it only after a paired held-out comparison, not a vendor benchmark.

Apply these rules in order:

1. Select eligible lexical/vector candidates under the same source and model versions.
2. Fuse the bounded eligible candidate union without an arbitrary shared lexical/vector cutoff. Any branch-level pruning must demonstrate that it preserves useful complementary candidates, including exact-code-only and paraphrase-only hits. RRF is an ordering score, not answer confidence; calibrate evidence usefulness/abstention on answerable and no-answer cases after selection. A nearest neighbor always existing does not prove useful evidence exists.
3. Deduplicate exact governed spans. Do not collapse records across companies, audiences, customers, or independent sources merely because text matches.
4. Preserve relevant conflicting evidence and explicit verification/validity. Do not let popularity, repetition, or recency silently resolve a business disagreement.
5. Preserve fused direct-hit order while selecting whole document passages that fit; continue to later fitting candidates when an earlier passage is too large. Count source contributions across the final packet.
6. Add only permitted continuation passages within remaining budget, after direct hits. Return honest truncation/coverage feedback for authorized results.

Recency is optional for temporal relevance such as recent decisions, not a universal multiplier on policies and stable preferences. A reranker is an optional measured improvement after candidate quality is established; run it only on currently authorized text with permitted model egress. No generative planner is required for ordinary reads/searches.

### Native budgets and performance gates

The optional response `context` contains `format:"native-evidence-json-v1"`, the tokenizer identifier, `max_tokens`, `token_count`, and exact `text`. That decoded text is compact JSON with an `evidence` array. Each element contains ordered `item_id`, `revision_id`, `text` and `citation`; citations retain source revision, extraction set, passage and full locator, or null for a memory without a passage citation. Mutable observation timestamps are not in this evidence representation. The complete tentative envelope, including JSON wrappers, escaping and separators, is encoded at each admission decision. Counts of individual passages are not added as an exact substitute. Special-token spellings in evidence are ordinary text.

Token mode accepts whole authorized passages and whole memory records; an oversized candidate is skipped without consuming byte/source/parent/duplicate credit, allowing later fitting evidence. Byte-only memory excerpts retain their existing behavior. Existing authorization, currentness, source identity, 12-item and four-per-source guards still govern selection. Token work adds a maximum 82 candidate rows, 83 complete counts and 512 KiB per serialized envelope. Two process-global nonwaiting worker permits bound concurrent blocking tokenizer work and remain held through completion. A tokenizer/work failure fails closed without a semantic fallback retry. The 512 KiB bound applies to the counted context string, not the outer HTTP JSON, which also includes existing items and an escaped copy of that string; no 512 KiB outer-response guarantee is made.

Native `context.token_count` counts only that exact evidence representation. Host instructions, the full question, schema, history, provider framing and output reservation remain the caller's responsibility. Concatenation can change tokenization: count the complete host input after assembly, not a sum of component counts. Local serialized-request counts are planning measurements, not guaranteed provider billing or model capacity. No remote token-count call is required by native memory.

Proposed hybrid retrieval starts with at most 40 candidates per branch. The current API caps final hits at 12 and accepted passages per exact source at four. Search excerpt text defaults to 8,192 UTF-8 bytes with an operator maximum of 16,384. `router_with_search_limits` permits `1 <= default <= maximum <= 65,535`; an omitted `max_context_bytes` uses the configured default, while zero, null and requests above the configured maximum are rejected without clamping. Explicit 4,096-byte requests retain their budget. Whole passages are never shortened to fit. The supported 65,535-byte ceiling is opt-in, not a default or token allowance. These are response bounds, not a bound on scanned rows, complete serialized metadata or full-prompt tokens. The implementation/checklist owns current SQL candidate mechanics; do not freeze a transient benchmark row count as a permanent API contract.

Whole-passage packing can omit a relevant passage larger than the byte budget. Future ingestion must choose format-aware units compatible with retrieval bounds or provide an explicitly supported bounded source-detail path. Token-based chunk targets alone do not guarantee byte fit, especially across languages. Test an oversized sole relevant passage and preserve truthful truncation/incomplete feedback; a lossy cut through a table or exception is not a fix.

The current search holds a tenant `FOR SHARE` authority lock during authorized candidate work; readers may overlap but they block conflicting authority writes until release. Native mutations serialize on that tenant. The runtime has local SQL lock/statement timeouts, but production admission, pool-wait deadlines, per-tenant concurrency/storage/ingestion limits and operational capacity are separate unfinished work. Result caps and RLS do not provide resource isolation.

One concrete query-plan hotspot to measure is complete-set integrity checking: search aggregates passage count and content bytes for eligible active sets, and the exact selector checks corresponding totals. This can involve document-wide work even for a small result. Measure actual plans before optimizing; do not remove the fail-closed completeness invariant without an equivalent trusted activation/immutability proof and corruption tests.

Measure eligible corpus size, vector dimensions, query plans, SQL/pool/lock time, memory and concurrent readers/writers before changing the ordering model. If heavy candidate work moves outside the final short transaction, reacquire native authority and validate exact current dependencies before materializing output, with bounded retry. No network, parser or model call under a database transaction.

Use exact authorized vector search as the baseline. Add ANN only when it misses a measured budget; test filtered recall and underfill against exact results for sparse ACLs and small tenants. Index/partition/routing choices follow those measurements; physical index visits need not be tenant-exclusive, but only eligible candidates may leave the native boundary. Shared deployments also need per-tenant admission so one tenant cannot monopolize the pool or job capacity.

Include unrelated-tenant growth in those tests. A shared ANN index can change one tenant's recall/latency when another tenant grows; lexical corpus statistics may also affect ranking depending on the chosen BM25 implementation. Do not expose raw scores or global statistics as diagnostics, or claim perfectly tenant-independent ranking from an output filter alone. If measured interference exceeds the chosen quality/privacy/capacity budget, isolate the relevant index or tenant placement; do not create per-company infrastructure speculatively.

No shared query/result cache initially. An optional query-embedding cache must be bounded and scoped to privacy/egress and exact model configuration; it caches neither permission decisions nor answer evidence. Authorized immutable artifacts, model weights and prepared statements may be reused without turning reuse into authority.

### Derived descriptions and summaries

Descriptions and summaries are optional derived views:

- Tiny memories return directly; generating three summary tiers adds little value.
- Long documents may have a short discovery description and a source-backed summary. Keep direct passage retrieval in parallel so summaries are never the only route to detail.
- Collection overviews are later navigation aids, confined to one collection and compatible disclosure policy. They are not cross-department summaries of hidden children.
- A summary supports discovery or a qualified overview. Precise numbers, exceptions, approvals, and quotations require original cited passages. A lossy overview is not proof that an omitted exception does not exist.

Summary dependencies include exact item/source/extraction revisions. A collection overview additionally needs its included membership/content generation so adding a new item invalidates an apparently complete old overview. Store included coverage and whether omissions are known. Only disclose coverage the reader is authorized to learn. If any required dependency becomes stale or withdrawn, exclude the derivative until rebuilt; do not keep serving it because a background cleanup has not run.

Persisted summaries draw only from retention-authorized source material within the permitted collection and disclosure policy. Managed transient connected-resource text is excluded. Cross-collection synthesis belongs in the host's request context, not a persistent native summary with a silently broader audience.

Complete extraction means complete for a declared supported scope. Scanned text, diagrams, hidden sheets, comments, or unsupported formula evaluation must never silently count as extracted evidence. Production parsers follow ADR-0090; the test parser harness is not production upload support. Spreadsheet totals require a structured computation path with complete admitted input, not a top-k excerpt.

### Derived storage and reliable processing

#### Evolve existing records

| Existing foundation | Proposed addition when its slice starts |
| --- | --- |
| Collections, items and immutable revisions | Typed kind/verification/provenance where needed; reuse stable identities and current pointers |
| Source revisions, Extraction Sets and Source Passages | Versioned embedding representations tied to exact source span; retain structural locators and continuation metadata |
| Active extraction-set pointer | Separately tracked semantic coverage and selected model generation; lexical readiness remains independent |

Use dedicated typed relational records for embeddings and summaries when they exist rather than a generic key/value record that hides every invariant. Each embedding records tenant-qualified item/revision, optional source/extraction/passage identity, pipeline/model version, dimensions, input digest and processing state. Enforce foreign-key integrity, bounded values and unique representation identity. Reject non-finite vectors and mismatched dimensions. Digests stay internal and are not cross-tenant existence probes.

Pin one embedding model and distance/input convention initially. Choose it by evaluating paraphrases, relevant business languages, exact-name distractors, latency, cost, license and deployment constraints. A model name or benchmark leaderboard alone is insufficient. Candidate provider selection is a bounded implementation task; this design does not invent a model dimension or authorize new remote data transfer.

#### Processing state and consistency

1. Explicit save/correction commits its new revision, lexical representation, serving pointer, audit, and durable processing intent atomically. Acknowledge durable/lexical readiness separately from semantic readiness.
2. Claim bounded work with a lease and monotonically fenced attempt identity. The job binds purpose, tenant, actor/durable authority, exact inputs, consent/deletion generations, pipeline version, deadline, and idempotency identity. It stores no borrowed employee bearer token.
3. Validate current authority/input before expensive work; release database locks before sandbox or model execution. Enforce job/provider time, byte, retry and spend bounds.
4. Validate outputs, then reacquire the prescribed native locks and commit only if input versions, active state, attempt fence, consent and authority still match. An expired attempt cannot activate results after a replacement worker succeeds.
5. Retries reuse the same operation identity; incompatible revisions become `stopped_stale`. A repeated provider call may still incur cost after an uncertain response; unique database activation does not promise exactly one provider bill.

For managed uploads, completed original bytes must exist and be verified in Go-owned storage before an active source reference is published. Go-to-Rust operation delivery uses the existing intent/receipt protocol; its two databases are not one atomic transaction. Failed or incomplete parser extraction cannot activate. An activated complete lexical extraction may have pending embeddings; every semantic candidate must still belong to that exact active Extraction Set.

Private processing remains bound to the active native owner and applicable consent. Later shared processing needs an explicitly admitted, revocable collection/purpose delegation, with current delegation/input/disclosure checks rather than a borrowed uploader credential. The host decides shared ownership policy. Until that job contract is implemented, seeded shared content does not imply unattended production authority.

Select a PostgreSQL-backed job library through the proof of fit proposed in the [background-processing record](agentic-memory-discussion-record.md#background-processing-and-observability-findings--2026-09-06), including SQLx compatibility and crash/lease tests. Apalis and Underway are candidates, not previously verified selections. If enqueue cannot participate in the same SQL transaction, bridge durable intent with an idempotent dispatcher; do not introduce a save-then-best-effort-enqueue gap. This requirement does not automatically select a new queue service or Temporal for memory.

#### Reprocessing, summaries, and deletion

Changing parser/config creates a new complete Extraction Set; switching the active pointer immediately excludes old-set passages and vectors. Changing the embedding model builds a separate generation. Never compare a new-model query vector to old-model stored vectors, even when dimensions match. Serve one chosen model generation per search, backfill new representations, verify authorized coverage and quality, then switch the configured generation atomically. Return honest incomplete coverage where appropriate and retain a safe rollback generation only under normal retention/lifecycle rules.

Generate per-document summaries against exact current dependencies. Commit them only if those inputs still match. A collection overview additionally requires an unchanged collection content/membership generation. These checks prevent a late summary job from overwriting newer knowledge or omitting newly added source material while appearing current.

Forget immediately excludes the item and all derivatives through authoritative serving conditions; physical cleanup is subsequent work. Old jobs cannot reactivate it. Preserve independent sources and separately approved publications; do not promise erasure of the same fact everywhere. Native recovery must preserve identity and replay-safe deletion evidence; ConsultAI's Employee-specific offboarding and export rules remain host-owned.

### Native query and interface discipline

Keep the versioned HTTP/JSON interface. Introduce semantic readiness, hit reasons or new dependency selectors only with their tested capability; unknown request fields remain rejected. Current item reads cannot validate an active document Extraction Set on behalf of a host that reuses cached passages.

Use SQLx checked macros for static queries when that slice starts, retain offline metadata, verify it against a freshly migrated test schema, and run restricted-role behavioral tests. Macros do not prove stored-function authorization, prevent same-typed ID swaps or validate unsafe nullability assertions. Retain SQLx; no code generator or driver switch is required here.

Once deployed to persistent environments, migrations are immutable numbered changes with a verified upgrade path and explicit rollback/data-restoration strategy. Current fixture-reset/setup SQL is not production credential provisioning. Preserve the existing core's migration/test ownership; this design does not authorize rewriting it during another task.

### Failure and evaluation contract

Embedding outage permits current authorized lexical/direct fallback with semantic degradation; pending embeddings never make superseded revisions current. Optional reranker/summary failure uses authorized underlying evidence. Required identity/storage/dependency failures deny the affected operation. A nearest neighbor existing or a search returning no hits does not establish answer confidence or exhaustive coverage.

Measure native recall/citation fidelity and lifecycle enforcement separately from host answer quality/token cost. Deterministic vectors verify plumbing, not meaning. Test exact names and paraphrases, negation/contradictions, subject scope, no-answer distractors, sparse ACLs, large/oversized passages, set replacement, deletion and job races with authorized positive controls. Measure required evidence before ranking, after fusion and after packing so a missing candidate is not confused with a dropped passage or reader error. Compare lexical, hybrid and optional reranker/summary variants on fixed data and equal budgets before accepting extra complexity; use the staged evaluation protocol.

Record stage latency, pool/lock wait, permitted coverage, bytes, backlog, retries and stale cancellations. Keep query/source text, bearer credentials and sensitive model payloads out of ordinary telemetry; scoped diagnostics and private activity inventories require separate authority. No production scale or token-saving percentage is inferred from the synthetic pilot.

## Review outcome and entry gates

The native first-core contract is fixed and has bounded implementation evidence in the checklist. Semantic retrieval, production ingestion, managed authority, complete host dependency validation, operational recovery and model-quality/token-cost claims require separate gates. This document supplies requirements, not a blanket readiness verdict. The [current boundary review](agentic-memory-domain-review.md#current-boundary-review--2026-09-07) records remaining issues.
